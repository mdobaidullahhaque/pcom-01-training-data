# pcom-01-training-data

Training dataset following the PCOM-01 record schema. Each row is one npm package version at a prediction date, labelled with the new GitHub Security Advisories (GHSAs) for that package in the next 90 days.

- **Prediction date (t0):** 2025-08-01T00:00:00.000Z
- **Features:** only data from before t0, with monthly series over the 12 full months before it
- **Targets:** new GHSAs published in [t0, t0 + 90 days), up to 2025-10-30, by severity
- **Size:** 1,912 rows, 225 columns (224 PCOM-01 core columns plus `prediction_date`), 26 positive rows (1.4%)

## How to reproduce

Needs Python 3.12 or newer (tested with 3.15.2 on Windows); the pinned numpy needs at least 3.12. `GITHUB_TOKEN` must be set to a read-only token for the GitHub step; it is read only from the environment. Raw responses are cached in `data/cache/` (gitignored).

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

python -m src.advisory_snapshots --only latest t0 target_end
python -m src.advisories data\cache\advisory-db\latest
python -m src.advisories data\cache\advisory-db\t0
python -m src.advisories data\cache\advisory-db\target_end
python -u -m src.select_packages
python -u -m src.npm_meta
python -u -m src.github_activity
python -u -m src.run_initial
python -u -m src.build_dataset
python -m pytest
```

An exact rebuild is not guaranteed. The time budget depends on network speed and the cache, so a rerun can reach a different number of packages, and npm and GitHub data change over time. `data/packages_included.csv` records exactly which packages this version contains.

## Main decisions

- **Month index:** M0 = July 2025, the most recent full month before t0, and M11 = August 2024. Set by `M0_IS_MOST_RECENT` in `config.py`; not yet confirmed against the course sheet.
- **Version in `purl`:** highest stable semver version published before t0, else the highest version before t0. It must still have a manifest. Exact npm names are kept, including legacy uppercase ones.
- **Qualifying GHSA:** GitHub-reviewed, not withdrawn in that snapshot, and naming exactly this npm package.
- **Snapshots:** features and their severities use the advisory database as of t0 (`41c89aa`). Targets and their severities use it as of the end of the window (`abfbb63`). An advisory published before t0 but reviewed after it counts as neither.
- **Strata (seed 42), chosen using only pre-t0 information:**
  - A `had_ghsa`: all packages with a qualifying advisory before t0.
  - B `popular_no_ghsa`: from `npm-high-impact@1.11.0`, at least 1,000,000 downloads in the feature year.
  - C `random_no_ghsa`: from `all-the-package-names@2.0.2159`, 1,000 to under 1,000,000 downloads in the feature year.
- **CWE-506 (malware, account takeover):** kept as normal GHSAs. They are flagged by `is_cwe506` in the advisory cache table, which is not part of the 225 columns.
- **Security placeholders:** rows whose chosen version matches `0.0.x-security` are kept and flagged in `data/packages_included.csv`. Their GitHub columns are NULL, because they all share one repo.
- **Downloads:** days before a package existed are not counted as observed. A month with no observed days has NULL downloads.

## Limitations

- **Time budget:** this initial version covers 1,912 of the 3,771 selected packages (A 1,388, B 258, C 266). A 40-minute metadata budget left 1,840 unreached, and 19 reached packages were skipped. Packages were shuffled across strata first, so the reached ones are not biased by stratum.
- **GitHub issue and PR columns are mostly NULL (99.5% of cells):** only 9 rows have them, all from the pipeline test list, so they are not a random sample. The rest are to be added later.
- **Few positive rows:** 26 of 1,912 (1.4%), 25 of them from stratum A. Most packages that get a first-time advisory are not in the sample.
- **Group A is partly placeholders:** 152 of its rows are security placeholders, so their metadata describes npm's placeholder, not the original package.
- **Monorepos:** packages in one repo share that whole repo's activity, which is not specific to the package.
- **Survivorship:** packages fully unpublished after t0 are skipped, and those with unknown downloads could not enter strata B and C. Issues deleted or transferred after t0 are invisible.
- **`unpacked_size` and `file_count`:** NULL in 359 rows, mostly older versions. Tarballs were not downloaded to fill them.
- **Spam:** no quality filter was applied, so some packages may be spam.
- **Defender:** 7 non-npm advisory files could not be read on the build machine. GitHub's current data shows they are not npm.

## Prediction function (pcom-entry-1)

Predicts the 5 `target_ghsa_*_count_90d` values for each package in a PCOM-01 CSV. It runs in about 1-2 seconds for 1,000 rows. For the live class round, see [docs/class_round.md](docs/class_round.md).

### Setup on a fresh clone

```powershell
git clone https://github.com/mdobaidullahhaque/pcom-01-training-data
cd pcom-01-training-data
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

The install downloads about 80 MB and took about 2 minutes in a test with a warm pip cache; allow longer on a new machine. Python 3.12 or newer is needed.

Everything `predict.py` needs is in git: `predict.py`, `config.py`, `src/model/features.py`, `src/model/counts.py` and `models/pcom_entry_1/` (`model.txt`, `model_meta.json`). No network access and no `GITHUB_TOKEN` are needed. `.gitattributes` stops git from converting the model's line endings. `predict.py` also normalises them, and checks the model against the SHA-256 hash in `model_meta.json` before loading it.

**Known issue in the tag `pcom-entry-1`:** that version has no `.gitattributes`, the hash check or the line-ending fix. On a Windows clone with `core.autocrlf=true`, git converts `model.txt` to CRLF, and LightGBM then crashes while loading it, with no output file. Later commits fix this. A working copy whose `model.txt` has LF line endings is not affected.

### Usage

```powershell
.venv\Scripts\python.exe predict.py input.csv
.venv\Scripts\python.exe predict.py input.csv -o output.csv --strategy S0
.venv\Scripts\python.exe predict.py input.csv --float
```

- **Input:** a CSV in the PCOM-01 record schema. Comma or semicolon, UTF-8 with or without BOM (Windows-1252 as a fallback), column names in any order or case. Extra columns are ignored, and missing columns or values are treated as unknown. Rows where every cell is empty are skipped, with a notice.
- **Output:** `<input name>_predictions.csv` next to the input, unless `-o` is given. It holds exactly `target_ghsa_low_count_90d`, `target_ghsa_moderate_count_90d`, `target_ghsa_high_count_90d`, `target_ghsa_critical_count_90d` and `target_ghsa_unknown_count_90d`, as non-negative integers, one row per input row, in the same order. The screen shows the same numbers with each row's `purl` and score.
- **Values for the form (float):** a second table on screen shows the float values (3 decimals) for each package, from the float strategy named above it (HRMAX by default since Homework 7; see "Homework 7 refinement"). These are the numbers to type into the class form, which asks for floats.
- **`--float`:** writes the float values (6 decimals) to the output CSV instead of the integers.
- **`--float-strategy EV|HR|HRMAX`:** chooses the float values (default: `default_float_strategy` in `model_meta.json`, HRMAX). `EV` gives the pcom-entry-1/2 values.
- **`--strategy`:** chooses the integer counts: `S2` (default) or `S0` (all zeros). `S1` is also accepted, but it predicts all zeros on this data too.
- **Exit codes:** 0 = done; 1 = output written, but some or all rows fell back to zeros (for example, the model files are missing or do not match their hash); 2 = the input could not be read or the output could not be written.

### How it works

1. `src/model/features.py` turns each row into 25 features: sizes, dependency counts, days from package creation to release, download totals and trend, release activity, and GHSA history before t0.
2. A small class-weighted LightGBM model (4 leaves, 100 trees) gives a probability of any new GHSA in the next 90 days.
3. Scorer D: `score = ghsa_total + 0.5 × probability`. The past GHSA count comes first, and the probability only breaks ties.
4. Rule S2: `score >= 6.26` predicts 1 moderate advisory, otherwise all zeros. Unknown is always 0.
5. EV: the score falls into one of 4 buckets (0-1, 1-3, 3-6.26, 6.26 and above), and each bucket predicts the average count per severity among training packages in that bucket. For the top bucket that is low 0.061, moderate 0.364, high 0.121, critical 0.030 and unknown 0.
6. The counts are written in schema order.

### Results

Out-of-fold results from 5 × stratified 5-fold cross-validation on the 1,912 training rows (mean ± standard deviation). Random PR-AUC = 0.014.

| Scorer | PR-AUC (main) | ROC-AUC | Precision@50 | Recall@50 |
|---|---|---|---|---|
| Rule: `ghsa_total` | 0.282 ± 0.000 | 0.849 ± 0.001 | 0.240 | 0.462 |
| LightGBM alone | 0.197 ± 0.024 | 0.862 ± 0.007 | 0.184 | 0.354 |
| C: rank average of rule and LightGBM | 0.281 ± 0.027 | 0.877 ± 0.002 | 0.228 | 0.438 |
| **D: rule, LightGBM breaks ties (used)** | **0.293 ± 0.002** | 0.870 ± 0.001 | 0.240 | 0.462 |

The simple rule beat LightGBM alone on the main metric. With only 26 positives, 25 of them in stratum A, past GHSAs carry most of the signal, and a trained model cannot add much on its own. LightGBM still helps as a tie-breaker, especially among the many packages with no past GHSA.

**Counts strategies, on the out-of-fold scores:**

| Strategy | MAE, summed over 5 columns | Exact match | Precision (any) | Recall (any) | F1 (any) |
|---|---|---|---|---|---|
| S0: all zeros | 0.019 | 98.6% | 0 | 0 | 0 |
| **S2: threshold (default)** | 0.027 | 97.9% | 0.36 | 0.46 | 0.41 |

S2's threshold was chosen on the same scores it is evaluated on. Choosing it on 4/5 of the rows and testing on the rest gives F1 0.38.

**Error of the values typed into the form**, on the out-of-fold scores (cross-validated in brackets, fitted on 4/5 and tested on 1/5):

| Strategy | MAE, summed over 5 columns | MSE, summed over 5 columns |
|---|---|---|
| S0: all zeros | **0.0188** (0.0188) | 0.0282 (0.0282) |
| S2: threshold, integers | 0.0267 (0.0262) | 0.0329 (0.0324) |
| **EV: expected values (form default)** | 0.0337 (0.0352) | **0.0256** (0.0278) |

All zeros has the lowest absolute error and EV the lowest squared error, so type EV values unless the round is announced to be scored by absolute error.

### Rebuild the model

```powershell
.venv\Scripts\python.exe -m src.model.build
```

This runs cross-validation, trains the final model, fits the counts rule, and writes `models/pcom_entry_1/`. It takes about 25 seconds, and a rerun gives identical files.

### Limitations

- **Very few positives:** 26 positive rows, so every metric is uncertain.
- **Sampling:** stratum A (packages with an earlier GHSA) dominates the data and holds 25 of the 26 positives. The model has learned little about packages without a GHSA history.
- **Unknown severity:** always predicted as 0, because it never occurs in the training data.
- **Unknown scoring method:** the values were chosen without knowing how the round is scored. EV fits squared error, all zeros fits absolute error, and S2's integers fit detection, so none is best for every scoring method. EV's advantage over all zeros on squared error is small once cross-validated (0.0278 vs 0.0282).
- **EV is coarse:** it has only 4 buckets, so every package in a bucket gets the same 5 values.
- **M0 assumption:** M0 is assumed to be the most recent month before the prediction date. If the round's data uses the opposite order, the "last 3 months" and "months since" features are read in reverse.
- **One prediction date:** the model is trained on a single t0 (2025-08-01) and assumes the round's data follows the same definitions.

## Homework 7 refinement

Automated round 2 scored 5.35 (lower is better; rank 10 of 11, best 0.78). The round packages are busy and hot: the round 1 package has 26 past GHSAs, 18 of them in the last 12 months. EV's top bucket predicts only 0.36 moderate for every such package.

**New float strategies** (`src/model/counts.py`, chosen by `default_float_strategy` in `model_meta.json`):
- **HR (half-rate):** per severity, the GHSAs in the last 12 months (M0..M11) divided by 8, i.e. half of the 90-day rate.
- **HRMAX (default):** per severity, the larger of the EV value and the HR value. Packages without recent GHSAs keep the small EV values.
- **EV:** unchanged, kept for rollback.

**Error per row, summed over the 5 targets** (1,912 training rows; EV cross-validated, buckets fitted on 4/5; busy = 7+ past GHSAs, 31 rows; hot = 5+ GHSAs in the last 12 months, 5 rows):

| Strategy | MSE all | MAE all | MSE busy | MAE busy | MSE hot | MAE hot |
|---|---|---|---|---|---|---|
| EV | **0.0278** | 0.0352 | 0.920 | 0.738 | 2.861 | **1.496** |
| HR | 0.0281 | **0.0335** | 0.842 | **0.649** | 2.784 | 1.825 |
| **HRMAX (default)** | 0.0283 | 0.0482 | **0.840** | 0.786 | **2.770** | 1.847 |

HRMAX has the lowest squared error on busy and hot rows, and overall it is about level with all zeros (0.0282) and EV (0.0278). For the round 1 package it gives low 0.375, moderate 1.75, high 0.125, critical 0.030 and unknown 0 (EV: 0.061 / 0.364 / 0.121 / 0.030 / 0).

**Caveats:** the busy and hot groups are tiny (11 and 3 positive rows), the divisor 8 was chosen on this same data, the data is from 2025, and no training package is as hot as the round packages.

**Use and rollback:**
- `predict.py ... --float-strategy EV|HR|HRMAX` overrides the default; the screen shows `Float strategy ...`.
- The service logs `[run_model] strategy=HRMAX ...`. The environment variable `PCOM_FLOAT_STRATEGY=EV` (`docker run -e ...`) switches it back to EV without a rebuild; see `docs/vm_deploy.md`.
- The uploaded file is unchanged in form: 1 row, the 5 Prediction_Schema names, floats >= 0 with 6 decimals, all zeros if the input cannot be used.
